一句话概括：不借现成解析库，从零手写一个 sdb::elf 解析器（mmap 整个文件、解析节头/字符串表/符号表），并首次区分"文件地址"与"运行时虚拟地址"，顺带引入 sdb::target 这个符号层抽象。

本章在全书中的位置

前十章的调试器只懂字节和寄存器，从本章起它开始"识字"了。ELF 解析是通向源码级调试的第一级台阶：第 12 章的 DWARF 数据就藏在 ELF 节里，第 13 章行表、第 14 章源码级断点都建立在 file_addr/load bias 这套地址体系之上；第 17 章讲共享库加载时会回头补"段"那一半视角。作者的开场梗也值得会心一笑：他说的"神圣文本"是 System V ABI 规范，不是托尔金那张精灵语羊皮纸。

逐节要点（用自己的话讲）

1. What Is an ELF：节与段是同一份数据的两副眼镜

ELF 可以是可执行、共享库、可重定位文件（即静态库）和 core dump 四种形态。链接期信息用"节"（有名字、有标志位）承载，执行期信息用"段"（无名字、描述加载地址与权限）承载，二者是对同一块字节的不同视角，且不是一一对应——一个段可覆盖多个节，一个节也可出现在多个段。本章只做"节"这一半，"段"留到第 17 章程序加载时再讲。

2. ELF Header Parsing：用 mmap 偷懒的正确姿势

解析直接复用 Linux 自带的 elf.h 类型（Elf64_Ehdr 等），省去大量定义样板。sdb::elf 构造时 open + fstat + mmap 整个文件只读映射进虚拟内存——对几百 MB 甚至更大的文件不必真的读进来，内核按需换页。小坑：声明统计结构必须写 struct stat stats，因为全局命名空间里已有同名函数 stat。析构记得 munmap + close。

3. Section Header Parsing 与一个隐藏边界

节头表位置在 e_shoff、数量在 e_shnum。但节的数量超过 0xff00 时，ELF 规范约定 e_shnum 写 0、真实数量藏在第一个节头（索引 0，本是保留的 NULL 节）的 sh_size 里。作者专门处理了这个"大文件"分支——自己写解析器而不依赖现成库，正是为了看清这类规范边角。

4. String Tables：一切名字皆偏移

字符串表就是一串以 \0 结尾的字符串拼在一起，ELF 里所有"名字"都是指向它的字节偏移；表首必为 \0，所以偏移 0 永远表示空串，字符串还能共享子串。文件通常有 .shstrtab（节名）、.strtab（符号名）、.dynstr（动态链接）几张表。实现按名字查节（get_section/get_section_contents）和查字符串（.strtab 优先、回退 .dynstr）。作者注明了简化假设：严格实现应跟随节头 sh_link 找所属字符串表，而不是假设全局一张表。

5. 三种地址与 load bias：本章最需要慢读的部分

作者区分了三种地址：文件偏移（file_offset）、文件地址（file_addr，ELF 里写的虚拟地址，相对加载基址）、运行时虚拟地址（virt_addr）。关键洞察是 load bias：文件里相邻的节因权限不同（.text r-x、.data rw-）映射到内存时会被 4KiB 页对齐拆出空隙，但空隙在文件视图和内存视图中形状一致，所以整个文件只需一个整体偏移量即可换算——文件地址 + load bias = 虚拟地址。此前第 7、9 章靠 /proc/<pid>/maps 手工加基址的做法，在这里被体系化了。

6. Parsing the Symbol Table：两张表、两个索引

.symtab 是完整符号表，.dynsym 只含动态链接所需符号，被 strip 的二进制可能两者皆无，所以查找有回退顺序。每个符号（Elf64_Sym）有名字偏移、类型/绑定（打包在 st_info）、所属节、值和大小。作者建了两个索引：unordered_multimap（名字→符号，因重载/弱符号会重名；同时插入 mangled 和用 abi::__cxa_demangle 反出来的 demangled 名）和带自定义比较器的 std::map（地址区间→符号，比较器只看起点，从而能用 lower_bound 做"包含某地址的符号"查询——先查起点恰好相等的，再回退看前一个区间是否覆盖）。地址索引只收有名字、有地址且非 TLS 的符号。这是全书 C++ 密度最高的几页，慢慢啃。

7. Target 与 auxv：给调试器加"符号层"

新类型 sdb::target 承载符号级操作（管理符号断点、查调试信息等），底层低级操作仍归 sdb::process——这是清晰的两层架构分界。计算 load bias 这次不解析 maps，而是读 /proc/<pid>/auxv（内核传给用户态的 id/value 二元组数组，读到 AT_NULL 为止）：真实入口（AT_ENTRY）减 ELF 头里的 e_entry 就是加载基址。attach 场景用 /proc/<pid>/exe 符号链接定位可执行文件。最后把命令行层从 process 换成 target，停在断点时就能自动打印 (main) 这样的当前函数名——全书的"找回函数名"能力从此刻诞生。

8. Testing：三个快速 sanity check

测试验证：入口地址处的符号应是 _start（工具链提供的真实入口，由它再调 main）；按名字反查也要能找到它；再假装文件加载在 0xcafecafe，验证带 load bias 的虚拟地址查找正确。

结合你的背景给的建议

  • 你在 IDA 里"看节"是打开视窗点几下的事，这章是亲手把节头表从字节流里抠出来——差别在：IDA 帮你解决了基址重定位（rebase），而 sdb 要自己维护 load bias，这正是逆向工具与调试器的视角差。
  • file_addr / virt_addr / load bias 的三角换算值得画一张图贴墙上：静态分析时 e_entry 是文件地址，动态调试时 PC 是虚拟地址，两类工具互相传地址时忘减/加 bias 是经典事故。
  • C++ 符号 demangle（__cxa_demangle、Itanium ABI）你平时靠 Frida/IDA 自动完成；这章顺带看清了 mangled name 里编码的命名空间和参数信息从哪来。
  • mmap + 内存中直接解析的读法，与你熟悉的"把整个文件读进 Python bytes 再 struct.unpack"思路一致，但注意 C++ 这边 span/string_view 全是零拷贝视图，别让被引用对象先于视图析构。
  • 细节控可对照 readelf -S 输出手算一次 .text 的 sh_addr/sh_offset/sh_size，验证 get_section_containing_address 的区间判断；实验环境仍需 Linux/WSL2（auxv、/proc/<pid>/exe 都是 procfs 设施）。

与后续章节的衔接

本章的 elf 类只是"容器"，下一章开始往里装真正的货物：DWARF 调试信息（作者预告其复杂度远超 ELF，将横跨多个章节），其数据本身就躺在 ELF 节中；第 13 章行表负责"地址→源码行"，第 14 章源码级断点终于让 break 命令接受函数名和行号；而第 17 章共享库会复用本章全部机制并补上"段/程序头"的另一半——届时每个加载的 .so 都是一个新的 sdb::elf 实例。
